# 第 2 章 初识 Skills：它到底是什么

## 2.1 Skills：给模型装上“参考手册”

Skills 本质上是给 AI 模型外挂的一个文件夹，文件夹中通常包含如下内容：

1. **使用说明（`SKILL.md`）**：告诉 AI 何时使用这个技能，以及具体操作方式。
2. **参考资料**：例如公司的数据库结构图、API 文档。
3. **工具脚本**：例如一段写好的 Python 脚本，专门用来处理 Excel 表格。

### 2.1.1 Skills 的最小单元是什么

Skills 的最小单元是一个名为 `SKILL.md` 的 Markdown 文件。这个看似简单的文件，实际上是 AI 世界中一个自包含的“能力单元”，如同软件工程中的一个函数或一个类。

#### 1. Metadata：技能的门面与索引

文件头部使用 YAML 格式定义元数据（被 `---` 包裹）。这不仅是简单描述，更是技能的“名片”和“搜索标签”。示例如下：

```yaml
---
name: "高级财务数据分析师"
description: "专门处理企业财务报表分析，能够自动识别异常数据点，计算关键财务比率，并生成合规的分析报告。适用于季度财报审查、投资尽职调查等场景。"
---
```

为什么 Metadata 如此关键？Agent 在面对复杂任务时，不会逐个阅读所有 Skills 的完整说明书，而是快速扫描可用 Skills 的 Metadata，就像项目经理浏览团队成员简历，快速判断“应该把这个任务交给谁”。

#### 2. Instructions：能力的内核与灵魂

Metadata 决定“是否调用”技能，Instructions 则决定“如何正确执行”技能。

结构化操作指南与自由发挥的提示词不同。Skills Instructions 遵循严谨的结构：

```markdown
## 操作流程

### 第一阶段：数据准备
1. 验证输入文件的格式和完整性。
2. 进行基础数据清洗（去除空值、纠正明显错误）。
3. 标准化财务术语（确保中美会计准则术语统一）。

### 第二阶段：核心分析
1. 计算以下关键指标：
   - 盈利能力：毛利率、净利率、ROE、ROA
   - 偿债能力：流动比率、速动比率、资产负债率
   - 运营效率：应收账款周转率、存货周转率
2. 异常检测算法：
   - 使用 Z-score 方法识别异常数据点。
   - 对比行业基准值，标注显著偏差。
   - 标记连续季度趋势异常。

### 第三阶段：报告生成
1. 按照证监会要求的标准格式组织内容。
2. 高风险项目必须用红色高亮标注。
3. 添加免责声明和报告有效期。
```

完整的 `SKILL.md` 文件如原文图 2-1 所示，包含 Metadata 和 Instructions 两个主要部分。

#### 3. `SKILL.md` 与普通提示词的本质区别

1. **确定性 vs. 概率性**：`SKILL.md` 追求确定性的操作流程，要求 AI 严格按照既定步骤执行；普通提示词允许 AI 发挥“创意”，输出结果具有一定不确定性。
2. **结构化 vs. 自由化**：`SKILL.md` 通过明确章节划分和编号系统，使 AI 能准确定位当前执行到哪一步；普通提示词通常采用线性叙述，AI 需要自行理解任务流程。
3. **可验证 vs. 需评估**：`SKILL.md` 的每个步骤都有明确成功标准和验证方法，例如输出格式校验、返回码检查；普通提示词的结果通常需要人工评估“回答得好不好”，缺乏客观判定依据。

### 2.1.2 Skills 与提示词库的区别

很多刚接触 AI 开发的从业者会困惑：Skills 不就是更高级的提示词吗？它和 GitHub 上的提示词库（Prompt Library）有什么区别？

简单来说，提示词库是需要手动复制、粘贴或选择的静态指令模板；Skills 是 Claude Code 自动识别并调用的动态能力包，包含指令、代码和文件。

#### 1. 触发方式：自动 vs. 手动

Skills 系统可自动识别和调用，用户无须显式运行。当用户请求，例如“帮我分析这个 Excel”，与某个 Skills 的描述匹配时，Claude 模型会自动决定是否激活并使用该 Skills。

提示词库通常需要手动调用：用户自行判断何时使用特定提示词，然后手动输入或粘贴来触发它。

#### 2. 上下文加载与 Token 消耗：渐进式披露 vs. 一次性加载

这是两者在架构上的核心区别，直接影响 Token 消耗。

Skills 采用渐进式披露机制。启动时，Claude Code 只加载 Skills 的名称和描述，Token 消耗很少；只有当 Claude 模型决定使用某个 Skills 时，才读取其具体指令。

若 Skills 包含大量参考资料，例如 API 文档、数据库结构，Claude Code 只有在确实需要时才读取这些文件。

提示词库通常需要将完整指令、背景信息和规则一次性加载到对话上下文窗口中。若提示词很长，例如包含大量规则的“清洗医疗数据”指令，会立即消耗大量 Token，即使当前任务只需要其中一小部分。

#### 3. 能力边界：可执行代码 vs. 纯文本指令

Skills 是文件系统级实体，可包含可执行脚本，例如 Python 或 Bash 脚本，用于处理复杂逻辑，如数据清洗和格式验证。这种工作机制比让大语言模型现场生成代码更可靠、更高效。

提示词库主要是纯文本指令。虽然可以通过提示词让 AI 生成代码，但无法像 Skills 那样直接携带并运行预先编写、经过测试的本地脚本。

#### 示例：每周销售周报

使用提示词库（Prompt Library）：

1. 打开 ChatGPT。
2. 从 Prompt Library 复制“销售周报生成 Prompt”（约 800 字）。
3. 粘贴到对话框。
4. 附加上周销售数据。
5. 等待生成。
6. 手动调整格式。
7. 复制到 Word 文档。

耗时：约 30 分钟/次，且质量不稳定。

使用 Skills：安装 `sales-weekly-report` 技能后，每周一操作人员只需要说：“生成销售周报”。

Agent 自动：

1. 调用技能。
2. 从数据库提取最新数据。
3. 按技能定义的模板生成报告。
4. 发送到指定邮箱。

耗时：约 2 分钟，质量完全一致。

总而言之，Skills 是提示词的工程化进阶。若业务中需要反复向 Claude Code 粘贴相同的长指令，或需要 Claude Code 遵循复杂的标准作业程序（SOP）来处理文件和数据，就应将这些提示词升级为 Skills。这样 Claude Code 能像拥有“肌肉记忆”一样，在合适时机自动应用专业知识，而无须每次从头学习。

### 2.1.3 Skills 与 Agent 的协作机制：调用关系解析

理解 Skills 与 Agent 的调用关系，是掌握 Agent 架构的关键，也是实践中认知误区最集中的领域。核心原则可以概括为 **Model-invoked（模型调用）**。

在这一范式下，技能选择权归 AI 模型本身，而非人工预先指定。这类似专业助理的工作模式：管理者无须逐项指示“查阅数据表、制作演示文稿、撰写邮件”等具体操作，只需提出“准备明天的董事会汇报材料”的宏观目标；具体规划路径与工具选择由助理依据专业判断自主完成。

当用户提出“将 PDF 文件中的表格转换为 Excel 格式”时，Agent 内部遵循以下流程。

#### 1. 意图理解与技能匹配

```text
用户输入：将 PDF 文件中的表格转换为 Excel 格式

Agent 思考：
需要完成：
1. 处理 PDF 文件
2. 提取表格
3. 转换为 Excel 格式

技能检索：搜索技能库中与“PDF”“表格”“Excel”相关的技能。
匹配度评分：pdf-table-extractor 95 分；document-converter 80 分；……
选择最佳技能：调用 pdf-table-extractor。
```

#### 2. 技能加载与参数绑定

```text
Skills：pdf-table-extractor
输入参数解析：识别到用户上传了 PDF 文件。
上下文准备：将 PDF 文件内容、用户指令和技能说明书加载到工作内存。
```

#### 3. 技能执行与结果返回

```text
按 Skills 指令执行：
1. 使用 OCR 模块识别 PDF 中的表格区域。
2. 提取表格数据并结构化。
3. 验证数据完整性。
4. 生成 Excel 文件。

结果格式化：已成功提取 3 个表格，生成 Excel 文件：result.xlsx。
用户对话延续：文件已生成，是否要进一步分析这些数据？
```

## 2.2 核心价值点：省 Token、可复用、可治理

在探讨“省 Token、可复用、可治理”等核心价值时，重点不在理论，而在通过设计机制将它们转化为实际工程实践。其中最直接的体现，是优化与大语言模型的交互方式，告别冗长、低效的单体提示词，实现高效且灵活的新范式。

这一实践的核心思想是“渐进式披露”：一种广泛应用于交互设计的经典原则，即只在需要时展示必要信息，避免一次性呈现所有复杂细节造成认知过载。将此原则迁移至 Agent 与 Skills 的管理中，带来了效率提升。

### 2.2.1 减少重复解释

#### 1. 以人类大脑的记忆机制类比

想象一位大学教授，需要管理几十门不同学科的知识。他不会把每门课的完整讲义都随时装在脑子里，否则大脑会不堪重负。相反，他只需记住：

1. **课程目录**：每门课的名称和简短描述。
2. **调取方式**：每门课的讲义放在图书馆的哪个书架。

当有学生问及“量子力学”时，教授不需要立即背诵薛定谔方程，而是知道“这门课教过，讲义在图书馆三楼物理区”，再去取用。这就是渐进式披露：按需加载知识，而不是预加载所有内容。

Skills 正好运用了这一理念，其管理方式分为两个层次。

#### 2. 第一层：技能索引（100 Token 以内）

系统启动时，Agent 只加载所有 Skills 的“名片”，即每个技能的 Metadata。这些名片就像课程目录中课程的名称和简介，以极少的 Token 消耗，让 Agent 快速知晓有哪些技能可供调用。

例如，一个智能客服系统的技能可能包括“常见问题解答”“订单查询服务”“产品信息提供”等。系统启动时，技能索引层只加载这些简要标识，不加载具体解答话术、查询逻辑和产品信息细节。

#### 3. 第二层：按需加载（5000 Token 以内）

当用户提出具体需求时，Agent 根据技能索引定位相关技能，然后按需加载该技能的完整执行逻辑、参考文档和操作规范。

例如，用户询问“如何查询订单状态”时，Agent 根据技能索引定位“订单查询服务”技能，随后加载详细内容，包括订单查询流程、数据库接口调用和可能的异常处理等。该过程小于 5000 Token。

#### 4. 现实世界的收益计算

假设存在一个企业级 AI 系统，对比两种方式的 Token 消耗：

**传统提示词（Prompt）方式：**

1. 必须将所有业务流程写入一个 Prompt：约 50,000 Token。
2. 单次调用费用：$0.50（依据 GPT-4 价格计算）。
3. 响应速度：较慢，需要处理大量上下文。

**Skills 渐进式披露方式：**

1. 技能索引：100 个技能 × 100 Token = 10,000 Token。
2. 实际加载：当前任务所需 2 个技能 × 3,000 Token = 6,000 Token。
3. 总上下文：11,000 Token，比 50,000 Token 减少 78%。
4. 单次调用费用：$0.11，成本降低 78%。
5. 响应速度：明显提升。

随着技能库持续扩展，两种实现方式的差异会被放大。传统大提示词模式中，每新增一个业务流程，提示词长度都会显著增长，Token 消耗与响应延迟不断上升；而 Skills 的渐进式披露模式只需为每个新技能添加约 50 Token 的索引条目，核心处理负载和响应性能几乎不受影响。

### 2.2.2 知识复用与团队协作

#### 1. 知识管理的三个时代

1. **第一代：口耳相传（前数字化时代）**

   经验 → 口头传授 → 理解 80% → 再次传递 → 最终失真 50%

   特点：容易失真，无法规模化管理。

2. **第二代：文档与提示词（数字化初期）**

   创建完美提示词 → 存储在本地计算机 → 无法与团队其他人共享 → 创建者离职 → 知识消失

   特点：知识孤岛，难以复用。

3. **第三代：Skills 代码化管理（现代）**

   创建 `financial-analysis-skill` → 提交到 GitHub 仓库，PR Review → 通过 CI/CD 测试验证 → 发布到团队技能市场 → 团队成员一键安装 → 使用数据反馈 → 持续优化 v1.1、v1.2……

#### 2. Skills 如何实现真正的知识复用

##### 版本控制：不是备份，更是演进

Skills 的目录结构：

```text
financial-analysis-skill/
├── .git/                     # Git 版本控制
├── SKILL.md                  # 核心说明文档
├── scripts/
│   ├── ratio_calculator.py   # 财务比率计算脚本
│   └── anomaly_detector.py   # 异常检测算法
├── reference/
│   └── test_bank_statement_1.pdf
├── expected_output_1.json
├── asset/                    # 字体等资源
└── README.md                 # 使用说明
```

Git 提交记录展示了知识演进过程：

```text
commit 7a3b2c1 - "v1.2: 增加现金流量表分析模块" (2024-03-15)
commit 4d5e6f7 - "v1.1: 改进 ROE 计算逻辑，修正除零问题" (2024-02-28)
commit 1a2b3c4 - "v1.0: 实现基础财务报表分析功能" (2024-01-10)
```

每个 commit 都是知识的增量，而不是覆盖。若 v1.2 版本存在问题，可以轻松回退至 v1.1。

##### 团队协作：从线性传递到网状共享

**传统模式（线性）：**

任务被并行分发给不同能力层级成员，各自独立优化，缺乏交叉验证，最终输出质量参差不齐，需要额外人力整合，造成资源浪费与交付延迟。原文图 2-3 展示了这一过程。

**Skills 模式（网状）：**

Skills 架构通过 Git 化工程实践，将团队协作重构为网状知识沉淀网络。每位成员既是能力使用者，也是优化贡献者。

原文图 2-4 展示了 Skills 驱动的闭环知识进化机制：初级成员不再各自维护独立版本，而是通过 PR 向统一的核心技能库提交优化，例如算法改进或功能扩展。所有修改均经 CI/CD 流水线自动测试验证，确保质量基线不被破坏。验证通过后，新版本自动分发至全体团队成员，实现“一人优化，全员受益”。

首席分析师作为维护者负责审核 PR（Pull Request，合并请求），但不垄断知识生产环节，从而形成“专家兜底 + 集体创新”的循环。技能从一次性交付物转变为可持续迭代的数字资产，每一次贡献都是团队知识的增量沉淀。

## 2.3 Skills 的适用边界

Skills 虽然强大，但本质是一种将确定性流程标准化的框架。理解它不适合做什么，比盲目应用更重要。

基本判断原则：Skills 适合高频、标准、可复用的任务；不适合低频、探索性、一次性任务。

### 2.3.1 一次性任务 vs. 可复用任务

想象你被邀请参加即兴演讲比赛，需要 AI 帮忙构思一个关于“人工智能伦理”的 3 分钟演讲稿。

使用传统 Prompt 方式：

```text
帮我构思一个关于人工智能伦理的 3 分钟演讲稿，
要引人深思，包含个人故事元素，适合大学生听众。
```

使用 Skills 方式则属于过度设计：需要创建完整技能、编写完整操作手册，再发布版本。

通过对比可见，传统方式只需一次性投入思考，即可获得可随时调整、重写或变换风格的演讲稿，也能充分结合当下心情与听众特点进行个性化定制。

若采用过度设计的 Skills 方式，则需要花数小时创建复杂规则和手册，不仅复用概率低，也会错失将时间投入其他重要任务的机会。

可通过以下公式评估是否值得创建 Skills：

```text
Skills ROI = (预计使用次数 × 单次效率提升) - 开发维护成本
```

是否为任务开发自动化 Skills，应基于成本效益分析。“预计使用次数”和“单次效率提升”决定总收益，再与开发成本比较，即可得出 ROI 和决策建议。

| 任务类型 | 预计使用次数 | 单次效率提升 | 开发成本 | ROI | 决策 |
| --- | ---: | ---: | ---: | ---: | --- |
| 每日销售报告 | 250 次/年 | 节省 15 分钟/次 | 8 小时 | +3750 分钟 | 创建 Skills |
| 月度董事会材料 | 12 次/年 | 节省 2 小时/次 | 20 小时 | 4 小时 | 考虑创建 |
| 个性化生日祝福 | 1 次 | 节省 5 分钟/次 | 2 小时 | -115 分钟 | 不用 Skills |
| 代码调试协助 | 50 次/年 | 节省 30 分钟/次 | 4 小时 | +1460 分钟 | 创建 Skills |

### 2.3.2 高度不确定的探索型任务

Skills 本质上是 SOP（标准作业程序），适用于确定性流程；探索型任务需要灵活试错，不适合被固定规则约束。

#### 场景 A：生产车间的装配线

```text
已知输入：零部件 A、B、C
已知流程：步骤 1 → 2 → 3 → 4
已知输出：成品 D
```

适用 Skills，因为这是确定性流程。

#### 场景 B：科学实验室的探索性研究

```text
未知输入：可能有杂质、干扰项
未知流程：需要尝试不同方法
未知输出：可能失败，也可能出现意外发现
```

不适用 Skills，因为这是非确定性探索。

场景 A 代表高度结构化的确定性任务，输入、流程和输出均明确，非常适合通过 Skills 将标准作业程序固化为可重复、可自动执行的模块。

场景 B 则属于开放性探索过程，充满不确定性与创造性，依赖灵活试错和临场判断，难以被预定义流程约束，因此不适合用 Skills 封装。

如何判断一个任务是否适合采用 Skills 范式？可对照以下三个维度。若任务在任一维度表现为“模糊”，则不适合封装为 Skills。

| 判断维度 | 模糊（不适合 Skills） | 清晰（适合 Skills） |
| --- | --- | --- |
| 目标 | 无法量化，例如“提高用户满意度” | 可量化，例如“将客户响应时间从 5 分钟降到 2 分钟” |
| 路径 | 无法定义，例如“不确定第一步做什么” | 可定义，例如有明确的 5 步流程图 |
| 结果 | 无法预测，例如“多种结果都可接受” | 可预测，例如“必须得到特定格式的结果” |

#### 案例 1：确定性的数据迁移（适合 Skills）

```python
task = "将 MySQL 用户表迁移到 PostgreSQL"

# 技能可以明确定义：
# 1. 连接源数据库
# 2. 导出表结构和数据
# 3. 转换数据类型（INT -> integer，VARCHAR -> text）
# 4. 导入目标数据库
# 5. 验证数据一致性
# 每一个步骤均为标准操作
```

#### 案例 2：探索性的市场机会分析（不适合 Skills）

```python
task = "找出我们的产品在东南亚的新市场机会"

# 没有标准答案，需要：
# - 创造性思考
# - 连接不相关的信息
# - 提出大胆假设
# - 尝试 -> 失败 -> 再试
# Skills 的规则会扼杀这种探索
```

## 2.4 本章小结

本章系统介绍了 Skills 的核心概念、架构价值与适用边界，为理解现代 AI 工程化实践奠定基础。

Skills 代表从“手工提示工程”向“标准化能力封装”的范式转变。它通过结构化封装、动态加载和团队协作三大支柱，解决传统 AI 应用中的 Token 浪费、知识孤岛和协作低效等核心痛点。

正确理解并应用 Skills，是构建高效、可维护 AI Agent 系统的关键一步。
